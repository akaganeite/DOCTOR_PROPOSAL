\section{国内外本学科领域的发展现状与趋势}

\subsection{基于智能体的漏洞挖掘}

\subsubsection{研究背景}

漏洞挖掘旨在识别目标系统中违反安全要求的程序行为，并提供支持缺陷判定与复现的证据。静态分析、符号执行和模糊测试分别从程序结构、路径约束和实际执行出发开展检测，形成相互补充的技术体系：覆盖率引导的模糊测试持续生成输入并保留有探索价值的测试用例，显著提高了自动化发现缺陷的效率；AddressSanitizer 等运行时检测机制为越界访问、释放后使用等错误提供了可复用的判据~\cite{fuzzingsurvey,asan}。这一体系的有效运行，还依赖目标可执行性、关键状态可达性以及错误是否具有可观察的判定依据。

大语言模型和智能体的发展正在降低代码理解、测试程序编写及分析工具编排的人工成本。Google 的 Big Sleep 已通过代码分析与工具交互，在经过长期测试的 SQLite 中发现未知内存安全漏洞；Mozilla 于 2026 年 4 月报告，使用前沿模型在初步评估中发现的 271 项漏洞已随 Firefox 150 修复~\cite{bigsleep,mozillafirefox150}。这些进展说明智能体已能参与成熟项目的实际安全分析，也表明内存安全问题尚未被普遍解决；在长期充分测试的特定组件中，仅继续增加同类输入变异的边际收益正在下降，新的增量能力更加依赖对深层程序语义与测试盲区的理解。因此，后续研究需要考察自动化能力尚未充分覆盖的任务条件。

相比能够通过崩溃、异常或崩溃报告直接暴露的内存错误，许多安全缺陷并不存在统一、显式的错误信号。例如，协议实现可能违反状态转移要求，权限状态可能在错误的会话间延续，资源也可能在生命周期结束后持续占用，而程序仍能正常执行。此类问题的关键不再只是能否触发新的执行路径，而是能否获得相应的安全要求，并据此判断实际行为是否构成违例，即测试预言（test oracle）问题~\cite{oracleproblem}。因此，本文重点关注协议与状态语义、访问控制和资源生命周期等需要结合行为约束才能判定的安全缺陷。

上述问题在嵌入式与固件场景中进一步受到分析条件的限制：仅能与设备交互时，内部状态、代码覆盖及资源对象通常不可直接观察；剥离符号的二进制需要恢复对象、功能与程序位置之间的对应关系；固件重托管后的行为也可能依赖外设响应、配置、定时事件与跨组件交互。Firmalice 和 Fuzzware 分别从二进制安全语义分析与硬件接口建模出发处理其中的部分困难，说明这些限制需要专门的程序分析与执行支持~\cite{firmalice,fuzzware}。

因此，本课题关注\textbf{在源码、符号、规约或运行时观察不完备的条件下，如何利用大语言模型的语义理解与交互分析能力，发现违反行为约束且能够在真实环境中成立的安全缺陷。}研究重点由单纯增加输入与路径覆盖，转向安全要求的获得、目标行为的辨识、状态违例的触发及其可信判定。

\subsubsection{研究现状与趋势}

传统漏洞挖掘主要依赖静态分析、符号执行和模糊测试，并逐渐从代码路径覆盖扩展到程序状态和安全性质。AFLNet、StateAFL 等工作利用协议响应或运行时状态反馈增强有状态程序的路径探索~\cite{aflnet,stateafl}；LTL-Fuzzer 等进一步将显式行为性质作为测试目标，搜索违反时序约束的执行轨迹~\cite{ltlfuzz}。这些方法提高了复杂状态空间中的探索能力，但通常需要预先定义状态表示、安全性质及其程序事件映射。对于缺少完整规约和语义信息的目标，如何获得可信的安全要求并将其转化为可执行的测试判据仍是重要问题。

大模型的发展进一步增强了漏洞挖掘中的输入生成和分析能力。Fuzz4All 利用 （Large Language Model，LLM）生成和变异测试输入，ChatAFL 则利用模型的协议知识生成消息并探索新的协议状态~\cite{fuzz4all,chatafl}。近期研究进一步将模型置于持续的工具交互过程中，使其参与代码理解、假设生成、测试和证据分析。相比传统模糊测试，这类方法显著增强了输入构造和分析过程的自动化，但“能够探索更多行为”并不意味着“能够正确判断安全违例”，安全假设和测试 oracle 的可靠性仍需独立解决。

这一问题在缺少源码和符号信息的二进制与固件场景中更加突出。BINREX 结合语义检索、分层规划和 IDAPython 工具调用实现任务驱动的二进制分析~\cite{binrex}；FirmAgent 则结合模糊测试与 LLM 污点分析，在固件中建立实际输入与潜在危险路径之间的联系~\cite{firmagent}。与此同时，Fuzzware 等工作通过建模 MMIO 等外部环境提高固件动态执行能力~\cite{fuzzware}。这些研究改善了语义恢复、路径定位和固件可执行性，但对于依赖历史状态、环境变化和多步交互的漏洞，仅恢复代码语义或提高执行覆盖仍不足以形成可靠的安全判据。

因此，近期研究开始进一步利用协议规范和历史缺陷知识提供安全语义。BSFuzzer 利用大语言模型从蓝牙协议规范中恢复状态机和报文语义，并据此构造字段和状态转移违例；ProtocolGuard 从协议规范提取约束，将其映射到源码并生成可执行断言进行验证~\cite{bsfuzzer,protocolguard}。另一类工作则从历史修复中提取可复用的行为约束，例如 TyPatch 利用 LLM 从 Linux 补丁中提取对象、动作、守卫和状态转移等类型状态转移规则~\cite{typatch}。这些工作说明，规约和历史补丁都可以为漏洞挖掘提供比代码覆盖更明确的安全要求，但现有方法通常依赖较完整的规范、源码或静态分析条件，如何在信息受限的二进制和设备环境中恢复并验证这些约束仍有困难。

此外，大量逻辑和资源缺陷并不会直接产生崩溃，使漏洞挖掘进一步面临“如何判错”的问题。LISA 通过生成API调用序列和程序不变式发现功能异常~\cite{lisa}，InferROI 则利用 LLM 推断资源获取、释放和可达性意图，并结合静态分析检测资源泄漏~\cite{inferroi}。这些工作表明，漏洞检测可以利用崩溃之外的行为和资源性质，但对于长期资源占用、状态错误和协议逻辑异常，仅观察执行结果、资源曲线或对象可达性通常不足以判断是否真正违反安全要求，还需要结合对象生命周期、历史状态和预期行为进行解释。

综合来看，漏洞挖掘正在由单纯追求输入和路径覆盖，逐步转向基于状态、规约和安全性质理解程序行为；大模型与智能体的发展又进一步增强了语义恢复、工具使用和测试生成能力。然而，现有能力仍主要分散在状态探索、规约提取、二进制分析、环境建模和定制 oracle 等不同环节。进一步需要解决的核心问题是：\textbf{在源码、规约和执行环境均可能不完整的条件下，如何获得可信的安全要求，将其映射为目标程序可观察、可执行的行为条件，并形成真实可达、可复现的漏洞证据。}

\subsubsection{研究挑战}

首先，\textbf{行为规约的可信获得}是语义漏洞挖掘的基础。协议规范、源码和历史补丁分别描述预期行为、实际实现和历史修复条件，其完整性、适用范围和可信度并不一致。已有研究表明，规约解释或上下文缺失会直接影响后续检测结果~\cite{protocolguard,typatch}。因此，在缺少完整规范时，需要区分明确规定的安全义务、具有独立证据支持的推断和待验证假设，避免直接将程序中的常见行为或模型生成的解释作为安全规范。

其次，需要解决\textbf{安全概念与目标程序行为之间的映射}。在缺少源码和符号信息的场景中，即使能够恢复函数语义，也仍需确定安全要求具体对应哪个对象、状态和程序位置，以及状态变化如何影响后续行为。BINREX 等工作增强了剥离二进制中的语义恢复能力~\cite{binrex}，但对于跨函数、跨任务和多组件共同维护的状态，仅识别函数功能仍不足以判断安全约束是否被违反。设备黑盒场景下内部状态进一步不可见，同一响应也可能对应不同内部状态，因此需要根据源码、二进制和设备等不同可观察条件建立不同层次的行为证据。

进一步地，状态性漏洞要求构造\textbf{真实可达的违例轨迹}。协议状态、资源生命周期和硬件环境通常由多次调用及外部事件共同决定，已有状态感知模糊测试能够增强多步交互探索~\cite{stateafl,chatafl}，但生成任意非法操作往往只会触发早期拒绝，并不能到达真正需要检查的状态。在重托管和模拟执行环境中，还必须区分人为构造的内部状态与攻击者能够通过合法外部操作到达的状态。只有能够说明目标状态的到达过程及其环境假设，异常行为才能形成具有实际意义的漏洞证据。

另一个核心问题是\textbf{缺少直接错误信号时的语义判定}。逻辑错误、协议违例和资源泄漏通常不会产生崩溃，需要通过不变式、断言或定制 oracle 判断行为是否违反安全要求~\cite{protocolguard,inferroi}。这类判据既不能过弱而遗漏漏洞，也不能过强而拒绝合法行为；资源类缺陷还涉及生命周期和观察窗口，例如未立即释放可能来自异步回收，资源增长也可能来自合法缓存。因此，需要同时定义预期安全行为和合法对照行为，并将候选发现与独立验证分离，使最终结论能够被重复执行和反驳。

最后，智能体化漏洞挖掘还需要从单点能力提升转向\textbf{完整发现过程的可靠评价}。代码覆盖、状态覆盖、性质监测状态和资源消耗都只能反映分析过程的部分信息，代理指标的提升并不必然意味着发现了更多真实漏洞。评价时还需控制源码、规约、历史补丁等输入条件，区分静态候选、可触发缺陷和经确认漏洞，并记录工具执行、环境构建和人工确认等成本。只有保持输入条件和证据标准一致，才能判断性能提升究竟来自模型能力、分析方法还是额外信息。

综上，智能体与大模型增强了语义理解、状态探索和工具使用能力，但并未消除规约缺失、状态不可见和非崩溃行为难以判定等根本问题。面向嵌入式设备和剥离二进制，本课题需要进一步建立\textbf{可信行为约束、真实可达交互与可靠语义判定之间的联系}，并以此连接行为规约、状态探索、可达性分析和漏洞判定。

\subsection{基于智能体的漏洞自动修复}

\subsubsection{研究背景}

漏洞修复是软件安全维护的重要环节，其目标除阻止已知攻击输入触发异常外，还需消除导致危险行为的程序缺陷，并维持正常使用所依赖的功能与安全约定。漏洞自动修复（Automated Vulnerability Repair，AVR）将漏洞分析、补丁生成与补丁验证组织为自动化过程，以降低安全维护对人工分析的依赖。与面向一般软件缺陷的自动程序修复（Automated Program Repair，APR）相比，AVR 更强调在攻击者可控输入、异常状态及安全敏感操作下恢复必要的安全条件。修复目标需要同时考察危险行为是否被有效约束、相关合法行为是否得到保留，代码修改是否合理、程序能否编译或已知失败是否消失只能作为局部指标~\cite{sokavr}。

漏洞修复通常发生在不完备信息条件下。漏洞报告、检测器告警和概念验证程序（Proof of Concept，PoC）能够提供分析线索，但不一定直接指出应修改的程序位置，也不一定完整描述正确修复应满足的条件。在漏洞修复中，已知 PoC 不再触发，可能只是某个特定输入或执行分支被阻断，漏洞根因是否消除仍需独立验证。由此，AVR 实际上包含两个相互关联的问题：\textbf{如何根据有限证据推断应当修复什么，以及如何验证生成的补丁确实满足修复要求}~\cite{sokavr,smith2015cure}。

LLM为处理漏洞描述、源代码和修复经验提供了新的技术途径。进一步结合代码检索、文件编辑、编译执行与测试工具，模型能够在智能体框架中逐步完成定位、修改和反馈驱动的修复。PatchAgent 等工作已经将这些环节整合到交互式系统中，推动研究对象从给定代码片段上的补丁生成扩展至真实项目中的自动修复~\cite{patchagent}。交互能力的增强提出了更高的语义理解要求：系统仍需判断告警位置与根因位置之间的关系、识别跨函数依赖，并区分补丁通过当前验证与恢复完整安全要求之间的差别。

Rust等系统编程语言使这一问题具有更丰富的语义层次。RustBelt 从形式化角度说明，基于不安全Rust代码 （\texttt{unsafe} Rust code） 实现的安全抽象需要满足相应验证条件，才能作为安全语言的可靠扩展~\cite{jung2018rustbelt}；针对真实 Rust 程序的研究也揭示了内存与线程安全实践中的复杂问题~\cite{qin2020rust}。因此，Rust 漏洞修复不仅涉及局部条件检查，还可能涉及所有权、生命周期、类型与 trait 约束、异常清理和并发状态。基于上述背景，本节围绕传统修复方法、LLM 与智能体修复、补丁正确性评价及 Rust 修复进展展开，重点讨论从漏洞表现恢复根因语义、从候选修改建立可信修复证据所面临的挑战。

\subsubsection{研究现状与趋势}

传统自动程序修复（Automated Program Repair, APR）已经形成了基于搜索、程序合成和语义约束等多种技术路线。GenProg 通过搜索程序变换空间寻找能够通过测试的候选补丁，SemFix 则利用符号执行和程序合成求解满足测试约束的修复表达式~\cite{genprog,nguyen2013semfix}。面向安全漏洞，ExtractFix 等工作进一步从漏洞执行中提取安全约束，并将其传播至候选修复位置以指导补丁生成~\cite{gao2021extractfix}。这类方法将修复从简单的测试通过推进到显式约束满足，但其能力通常受漏洞模型、程序分析精度和候选修复空间限制，对复杂跨过程语义和缺少明确错误信号的安全问题仍难以建立完整的修复条件。

大语言模型的发展显著扩展了漏洞修复中的候选补丁生成能力。VulRepair 等工作从历史漏洞补丁中学习漏洞代码到修复代码的映射；且零样本漏洞修复研究表明，通用代码模型无需针对特定漏洞类型训练，也能够根据漏洞代码和提示信息生成有效候选补丁~\cite{fu2022vulrepair,pearce2023zeroshot}。此后研究进一步引入漏洞上下文和根因信息，例如 APPATCH 结合静态依赖分析、根因推理和历史修复经验组织模型所需的代码上下文~\cite{nong2025appatch}。这些工作表明，LLM 修复正在由局部代码生成转向利用跨函数上下文和漏洞语义进行修复，但模型生成的补丁是否真正恢复安全性质仍需要程序级验证。

进一步地，修复系统开始从固定的生成流程发展为能够自主操作真实仓库的智能体。SWE-agent 展示了模型通过代码导航、文件编辑和程序执行完成复杂软件工程任务的能力，PatchAgent 等工作进一步将漏洞定位、补丁生成和测试反馈纳入持续的交互式修复过程~\cite{sweagent,patchagent}。这类方法使模型能够根据构建、漏洞复现和回归测试结果不断调整补丁，但多轮迭代也可能使补丁逐渐适配已有测试，而没有真正消除漏洞根因。因此，智能体自主性的提高并不能替代对补丁安全性的独立验证，修复位置、根因解释和最终安全性质需要分别考察。

与修复能力的发展相对应，真实漏洞基准逐渐从提供漏洞代码转向提供可复现的仓库级任务。Vul4J 为 Java 漏洞提供可执行的真实项目和漏洞证明测试，SEC-bench 则将类似任务扩展到真实 C/C++ 仓库，并探索自动化构建漏洞修复案例~\cite{bui2022vul4j,secbench}。这些基准为端到端修复提供了实验基础，但仅依赖已有 PoC 和功能测试仍面临经典的测试过拟合问题：补丁可以使已知触发失效并通过回归测试，却仍然没有恢复漏洞所要求的安全性质。

因此，近期研究开始加强补丁的独立安全验证。PVBench 利用官方修复新增的测试检查基础验证遗漏的漏洞相关行为，PatchBench 则通过额外漏洞输入和正常行为对照进一步检查补丁的安全性与功能保持~\cite{yu2026pvbench,shen2026patchbench}。这些工作表明，已知 PoC 消失并不足以证明漏洞被正确修复；同时，评估阶段能够使用的官方补丁和隐藏测试通常不应直接暴露给修复系统。因此，\textbf{修复过程能够获得的信息与独立评估所使用的安全证据需要明确隔离}，并进一步区分漏洞必要的安全要求与官方实现中的其他工程选择。

在这一方向上，本课题组前期构建了面向 Rust 真实漏洞的仓库级修复基准 \textbf{RRBench}~\cite{rrbench}，包含 115 个可复现漏洞案例。RRBench 将补丁评价划分为公开验证和私有验证两个阶段：公开阶段提供漏洞触发 PoC 与功能测试，私有阶段利用修复系统不可见的安全性质和合法行为检查验证补丁是否真正恢复漏洞要求。对代表性修复智能体的实验表明，通过公开验证的补丁中仍有 23.4\% 无法通过私有验证，并有 14 个案例未被任何配置正确修复。该结果说明，\textbf{端到端漏洞修复的关键问题已经不仅是生成能够通过测试的补丁，还包括如何理解漏洞根因、形成正确修复，并利用独立安全性质验证其正确性}，为后续研究“生成—验证”协同的漏洞修复方法提供了直接基础。

\subsubsection{研究挑战}

\subsubsection{研究挑战}

首先，复杂漏洞修复需要从不完备的定位信息中恢复\textbf{根因位置与必要上下文}。已有研究表明，漏洞触发位置与实际修复位置可能跨越不同函数，根因分析需要结合静态依赖和动态证据~\cite{li2024interpvd,nong2025appatch}。当上游仅提供崩溃位置、污点终点或局部告警时，系统仍需追踪状态的建立、传播和使用关系；同时，上下文过少可能遗漏关键依赖，过多又会引入无关信息。因此，关键问题是如何将初始定位线索转化为可验证的程序依赖证据，并据此动态确定分析和修复范围。

在此基础上，还需要保证\textbf{根因判断与修复策略之间的一致性}。漏洞类别和历史案例能够提供修复经验，但并不能直接确定目标程序中的缺陷对象、形成原因和正确干预位置。现有 LLM 修复方法已经利用根因推理和历史经验辅助补丁生成~\cite{nong2025appatch,wang2026kumushi}，但错误的早期解释也可能持续影响上下文选择和候选生成。因此，根因假设需要接受控制流、数据流、接口约束和执行证据的检验，并在证据冲突时重新定位或调整修复策略，而不是围绕单一假设反复生成相似补丁。

进一步地，正确修复要求恢复\textbf{跨接口和状态的安全性质}。真实漏洞的安全要求可能由多个函数、对象状态和调用阶段共同维护，尤其在 Rust 等具有丰富类型和生命周期机制的系统语言中，漏洞表现位置并不一定是安全约束应当建立的位置~\cite{jung2018rustbelt,qin2020rust}。修复不仅需要消除已知触发，还应确定安全性质由哪些操作共同维护以及是否存在绕过路径。对于部分漏洞，增强类型或接口约束也可能构成有效修复，因此评价时还需区分对危险行为的有意限制与对合法程序行为的意外破坏。

由此产生的核心问题是\textbf{如何将安全性质转化为独立、可执行的补丁验证}。已有研究通过额外漏洞输入、开发者新增测试和行为对照增强补丁验证~\cite{yu2026pvbench,shen2026patchbench}，但有限测试仍可能接受不完整修复，过强的检查又可能拒绝不同于官方实现的正确方案。因此，需要从漏洞根因中提炼必要的安全要求，将其转化为可执行检查，并同时设置合法行为对照。修复阶段可以利用公开测试和生成的反例持续迭代，但最终验证应与修复过程保持信息隔离，避免修复器针对隐藏判据过拟合。有限验证只能证明补丁满足已检查的安全要求，而不能排除未覆盖执行空间中的残余风险。

最后，智能体修复需要建立\textbf{统一且可复现的端到端评价标准}。现有研究在是否提供漏洞位置、是否要求仓库级分析以及采用测试、参考补丁还是人工审查等方面存在明显差异~\cite{secbench,shen2026patchbench}。评价时应明确系统能够获得的信息，分别记录补丁生成、构建、公开验证和独立安全验证结果，并保留无补丁、环境失败和预算耗尽等情况。同时还需要控制历史补丁泄漏以及模型、工具链和执行环境差异，并将上下文分析、候选生成和验证成本纳入评价，从而区分模型能力、额外信息和分析机制各自带来的收益。

综上，智能体漏洞修复已经从局部代码生成发展到真实仓库中的交互式分析，但可信修复仍依赖两个相互衔接的核心能力：\textbf{一是从不完备信息中形成有证据支持的根因判断并生成相应修复，二是将漏洞安全要求转化为独立、可执行且兼顾合法行为的验证条件。}本课题研究内容二围绕这一“生成--验证”协同过程展开，研究根因分析、候选修复与安全性质验证之间的联系，以提高复杂真实漏洞自动修复的可靠性。

\subsection{基于智能体的漏洞修复验证}

\subsubsection{研究背景}

漏洞修复是软件安全保障的重要环节，其目标除消除已知漏洞的触发条件外，还需要在维持合法功能的前提下阻断危险行为。围绕这一目标，自动漏洞修复（Automated Vulnerability Repair，AVR）研究形成了漏洞分析、补丁生成与补丁验证三个主要环节，采用程序分析、约束求解、程序变换和学习等技术降低对人工修复的依赖~\cite{sokavr}。随着大语言模型的发展，修复过程进一步由单一补丁生成扩展为交互式任务执行，PatchAgent 将缺陷定位、补丁生成与验证组织到同一智能体中，利用语言服务器和验证工具支持多轮修复~\cite{patchagent}。这些研究主要回答"如何产生有效修复"，软件系统的实际安全状态还取决于修复能否被正确集成并传播至最终部署的程序。

从软件供应链的角度看，漏洞修复远超上游提交补丁这一局部开发活动，它贯穿上游项目、下游分支、发行版、设备厂商与最终用户，构成一个持续维护过程。Li 和 Paxson 对安全补丁的研究表明，补丁开发需要同时考虑修复完整性与功能回归，安全修复也可能仅涉及少量代码变化~\cite{li2017largescale}。针对修复在相关仓库之间的传播，Machiry 等提出 SPIDER，通过分析补丁的行为影响，识别适合向相关项目传播的修复~\cite{machiry2020spider}；Zhang 等对 Android 内核补丁生态的研究进一步发现，修复在多层供应链中的传播可能存在较长延迟~\cite{zhang2021android}。因此，"补丁已经公开""下游已经合入"与"部署产物实际包含修复"是三个需要分别确认的状态。

版本信息和更新公告能够辅助判断修复状态，其覆盖范围存在边界。一方面，下游维护者可能将安全修复回移植至较早版本，同时保留原有上游版本号，Red Hat 的安全回移植实践明确指出，仅依据上游版本号开展漏洞扫描可能产生误判~\cite{redhatbackporting}。另一方面，闭源产品、固件和第三方二进制组件往往无法提供与部署产物完全对应的源码，使用者难以直接检查安全修复是否进入最终程序。由此，针对实际二进制开展独立的修复状态核查，成为连接补丁发布与安全维护的重要技术需求~\cite{fiber}。

补丁存在性测试（Patch Presence Testing，PPT）正是针对这一需求提出的：给定已知漏洞的修复信息，以及补丁状态未知的目标程序，判断目标中是否包含对应修复的实现证据。不同方法使用的参考材料有所区别，包括源码补丁、修复前后源码、参考二进制或中间表示等~\cite{fiber,binxray}。PPT 与通用二进制相似性检测的区别在于，后者主要寻找功能或结构相近的代码，前者则需要在高度相似的两个实现之间识别安全相关差异：一个边界条件、错误分支或参数处理的变化，可能不足以明显改变函数整体相似度，却足以改变其漏洞状态~\cite{binxray}。

需要区分的是，\textbf{PPT 核查"特定修复是否体现在目标程序中"，补丁正确性验证考察"修复是否充分消除目标缺陷并维持合法行为"。}即使检测到参考修复已经存在，也不能据此证明参考补丁本身完整，更不能推导出目标程序不存在其他漏洞~\cite{sokavr,li2017largescale,fiber}。因此，本节将 PPT 定位为漏洞修复生命周期中的部署侧验证环节，重点讨论其二进制证据提取、补丁语义匹配以及智能体化分析能力。

\subsubsection{研究现状与趋势}

早期补丁存在性测试（Patch Presence Testing, PPT）主要通过修复前后的局部语法和结构差异构造补丁特征，并在目标二进制中寻找对应证据。BinXray 和 PatchDiscovery 分别利用基本块映射、关键基本块及控制流结构描述补丁变化~\cite{binxray,patchdiscovery}。这类方法特征直观、匹配效率较高，但要求参考程序与目标程序之间保持较稳定的结构对应关系，容易受到编译优化、基本块重组和版本变化的影响。

为降低对具体指令形式的依赖，后续研究逐渐转向补丁语义建模。FIBER、PDiff 等方法利用符号执行、路径约束和程序状态描述补丁相关行为，PS\textsuperscript{3} 和 REACT 则进一步通过语义签名或中间表示增强不同编译配置下的补丁匹配能力~\cite{fiber,pdiff,ps3,react}。这些方法提高了 PPT 对二进制表示变化的适应能力，但分析结果仍依赖符号执行、IR 恢复和特征抽象的准确性，并通常需要目标函数或候选范围等定位信息。因此，稳定的补丁语义表示与准确的目标定位仍是传统 PPT 的两个关键问题。

除编译差异外，补丁本身还会随软件版本持续演化。已有研究表明，后续版本可能通过重构检查逻辑、移动代码或改变数据流重新实现同一安全修复，从而削弱基于原始补丁特征的检测能力~\cite{patchevolution}。这意味着 PPT 不仅需要适应同一实现经过不同编译过程产生的表示差异，还需要识别不同实现所保持的共同安全语义，检测对象也由具体补丁特征逐渐转向补丁所代表的安全行为。

大语言模型为跨源码与二进制表示的语义分析提供了新的途径。Lares 利用 LLM 将源码补丁切片映射到目标函数的反编译代码，并结合约束求解完成语义判断；PPTSP 则在语义规范化和关键路径提取后利用 LLM 处理难以通过传统特征区分的情况~\cite{lares,pptsp}。这些方法表明，模型能够辅助理解补丁语义并处理跨表示差异，但仍主要工作在预先给定的函数或候选范围内。从完整剥离二进制出发自主定位补丁相关代码、获取证据并形成最终判断，仍需要更完整的分析过程。

随着编码智能体的发展，PPT 可以进一步从固定分析流程转向交互式分析。智能体能够围绕补丁假设自主调用反汇编、检索和程序分析工具，在候选定位、局部检查和证据补充之间迭代。此时，系统能力不再仅由模型本身决定，工具接口、上下文信息、分析策略和资源预算都会影响最终结果~\cite{sweagent,aiagentsthatmatter}。因此，研究重点正在由单一补丁特征或模型输出扩展到完整的端到端分析过程，包括补丁定位、语义判断、证据获取以及分析成本。

围绕上述问题，本人前期已开展两项相互衔接的研究。首先，构建了包含 561 个 CVE、覆盖 10 个开源项目的 PPT 基准，并系统评估五款代表性工具，揭示了现有方法“高准确率、低决策成功率”的现象及其主要失败原因~\cite{zhang2026pptempirical}。进一步针对端到端场景，系统评估编码智能体在符号可见、剥离二进制、补丁演化和真实发行版软件包等条件下的 PPT 能力，发现前沿智能体仅使用基础二进制工具即可达到与专用方法相当的性能，但补丁定位和演化补丁识别仍是主要瓶颈~\cite{zhang2026agenticppt}。这些结果表明，PPT 的研究重点正在由\textbf{局部特征匹配}进一步转向\textbf{面向完整二进制的补丁定位、语义理解与证据验证}，为研究内容三提供了直接的研究基础。

\subsubsection{研究挑战}

首先，实际部署中的 PPT 需要解决\textbf{缺少定位提示时的补丁定位问题}。现有方法通常不同程度依赖符号、候选函数或外部定位结果~\cite{fiber,binxray,lares}，因此在已知函数范围内取得的匹配效果不能直接代表完整二进制上的端到端能力。分析系统需要从补丁语义出发定位相关函数和具体程序位置，并进一步确认相应检查是否真正作用于目标对象和危险操作；当存在多个相似候选时，还需要持续获取证据而非直接接受局部相似结果。

其次，\textbf{补丁演化会削弱原始修复特征与目标实现之间的对应关系}。已有语法签名、符号执行和 IR 方法能够缓解编译带来的表示差异，但后续版本可能通过重构控制流、数据流或错误处理方式重新实现同一安全修复~\cite{react,patchevolution}。因此，需要区分“原始补丁模式消失”和“安全修复失效”，从具体代码特征进一步恢复补丁所表达的安全语义，并根据检查对象、错误传播和危险操作之间的关系判断演化后的实现是否仍满足修复要求。

进一步地，引入大模型后需要保证\textbf{模型推理与程序证据之间的一致性}。Lares、PPTSP 等工作表明模型能够辅助跨表示定位和语义判断~\cite{lares,pptsp}，但自然语言解释本身不能作为补丁存在性的充分证据。最终判断需要能够回溯到具体指令、控制流和数据关系，并区分补丁不存在、漏洞相关功能不适用以及证据不足等不同情况，避免将检索失败、工具异常或模型推测直接转化为漏洞状态。

同时，PPT 系统还需要建立\textbf{统一的端到端评价方法}。不同研究在数据集、符号信息、候选函数和编译条件等方面存在差异，单独比较 Accuracy 或 F1 难以反映实际能力。评价应分别记录定位、语义判断和完整流程中的错误、无法判定及工具失败，并明确系统能够获得的信息条件，从而判断失败究竟来自补丁语义本身、定位能力还是工程实现，而不是将所有失败归结为算法精度。

最后，智能体分析还需要权衡\textbf{分析能力与资源成本}。更强模型、更多分析工具和更长上下文能够扩大证据搜索空间，但并不必然提高最终检测效果~\cite{sweagent,aiagentsthatmatter}。因此，需要在统一任务条件下比较模型能力、漏洞信息、工具配置和资源预算，研究如何利用低成本线索完成初步定位，并仅在证据不足时调用更复杂的程序分析，同时评价检测正确性、完成率和资源消耗。

综上，面向实际部署的 PPT 仍需要解决\textbf{补丁定位、演化修复识别、证据约束下的语义判断以及端到端可靠评价}等问题。本课题研究内容三将围绕这些环节，进一步研究程序分析与智能体推理的协同机制，提高复杂二进制场景下补丁存在性检测的可靠性与实用性。
