\section{拟采用的研究方法、技术路线、实验方案及其可行性分析}

\subsection{基于智能体的漏洞挖掘方法}

\textbf{拟解决的关键问题}：语义/逻辑漏洞（认证绕过、状态机错误、配置驱动缺陷）自动化挖掘的两大瓶颈——\textbf{自因变量难以统一建模}与\textbf{语义 oracle 难以自动构造}。自因变量——那些不受外部输入直接控制、由内部状态、配置、时序与外设决定的变量——在文献中以 state-driven、config-driven、timing-driven、peripheral-driven 等不同形态各自为战，缺乏统一抽象；同时，语义漏洞的判定依赖人工构造的策略与规约，Firmalice 的认证绕过 oracle 使用十年仍是孤例~\cite{firmalice}，oracle 的缺失使自动化检测难以规模化。

\textbf{技术方案}：针对上述问题，本文提出\textbf{自因变量感知的多智能体漏洞挖掘框架}，整体技术路线如图~\ref{fig:mining-route} 所示，包含四个核心模块：

\begin{itemize}
  \item \textbf{模块一：自因变量统一建模}。综合静态分析与智能体推理，在固件二进制上识别各类自因变量，并统一表示为标注来源类型、取值空间与影响路径的自因变量格，使后续 fuzzing 能够将自因变量作为一等探索维度。
  \item \textbf{模块二：语义 oracle 自动构造}。利用智能体从自然语言文档（协议 RFC、芯片数据手册、配置说明）中自动提取安全不变式，并将其编译为可执行的运行时监测点与断言，解决漏洞挖掘中"oracle 靠人工"的长期瓶颈。
  \item \textbf{模块三：自因变量感知的智能体 fuzzing}。采用规划—执行—验证三智能体协同架构：规划智能体根据覆盖率与不变式反馈规划探索策略；执行智能体在生成输入的同时，主动翻转目标自因变量；验证智能体检查不变式违背。该模块突破传统 fuzzing 仅在输入空间探索的局限。
  \item \textbf{模块四：漏洞确认与根因定位}。对验证智能体报告的候选漏洞，自动生成 PoC，通过动态切片定位根因，并提供人工审核接口。
\end{itemize}

\textbf{可行性分析}：（1）理论可行：自因变量概念已在 SyzTrust~\cite{syztrust}、Fuzzware~\cite{fuzzware} 等工作中以不同形态出现，本方案是对这些分散实践的统一与提升；（2）技术可行：多智能体协同架构已在 FirmAgent~\cite{firmagent} 中得到初步验证，LLM 的规约理解能力已在 ChatAFL~\cite{chatafl} 等工作中展现，"语义检索 + 可验证推理"的 agentic 范式已在通用二进制分析任务上被证明有效~\cite{binrex}；（3）工程可行：课题组在固件分析、智能体框架与 fuzzing 工具链上有完整积累，RRBench 的"角色分离智能体"设计模式可直接复用~\cite{rrbench}；（4）数据可行：可通过公开固件数据集与 FreeRTOS、Zephyr 等开源 IoT 项目获取评估对象，并可人工植入语义漏洞构建合成基准。

\textbf{实验方案}：基准包括 10--15 个含已知语义漏洞的真实 IoT 固件（含认证绕过、状态机错误等）与参考 LAVA-M 设计的 50+ 合成植入漏洞；对比方法包括 FIRM-AFL~\cite{firmafl}、Fuzzware~\cite{fuzzware}、FirmAgent~\cite{firmagent}、ChatAFL~\cite{chatafl}、AFLNet~\cite{aflnet}；评估指标包括语义漏洞发现数量、首次发现时间、假阳性率、自因变量覆盖率、oracle 自动构造准确率；消融实验分别验证自因变量建模、自动 oracle 与多智能体协同的独立贡献。预期语义漏洞发现数量相比最优基线提升 $\geq$ 5 倍，自因变量覆盖率 $\geq$ 70\%，oracle 自动构造准确率 $\geq$ 80\%。

\subsection{基于智能体的漏洞自动修复方法}

\textbf{拟解决的关键问题}：智能体漏洞自动修复的两大瓶颈——\textbf{部分规约下修复正确性难以验证}与\textbf{过拟合与回归难以系统抑制}。RRBench 大规模评估表明，现有智能体生成的"公开合理"补丁中 23.4\% 在私有安全性质检查下失败，且 14 个案例未被任何系统正确修复~\cite{rrbench}。其根本原因在于：修复环节缺乏对"修复意图"的语义判定能力，智能体容易生成仅抑制特定 PoC、却未消除漏洞根因的过拟合补丁，或在修复漏洞的同时破坏合法功能。

\textbf{技术方案}：针对上述问题，本文提出\textbf{修复—验证对偶的智能体漏洞修复框架}，核心思想是将 PPT 的"补丁语义判定"能力对偶迁移为"修复正确性验证"，整体技术路线如图~\ref{fig:repair-route} 所示，包含四个核心模块：

  \node[module, below=of m1] (m2) {%

\begin{itemize}
  \item \textbf{模块一：漏洞根因语义理解}。依托统一的漏洞语义五元组表示（与研究内容三共享），将漏洞报告与 PoC 转化为结构化的根因语义表示，为后续修复提供深层理解基础。
  \item \textbf{模块二：安全性质规约自动提取}。这是连接 PPT 与修复的关键创新。借鉴 RRBench 私有 Oracle 的设计思想，但将其从"人工构造"扩展为"智能体自动生成"：智能体基于漏洞语义与代码上下文，自动提取补丁必须满足的安全性质集合。这些规约既可指导补丁生成，也可作为最终验证依据。
  \item \textbf{模块三：规约引导的补丁生成}。修复智能体在根因语义与安全规约的双重引导下生成候选补丁，并通过编译、公开测试与静态检查进行多轮迭代。
  \item \textbf{模块四：PPT 式修复验证}。这是本研究内容的核心创新，将 PPT 能力对偶迁移到修复验证：通过\textbf{补丁语义判定}（验证候选补丁是否真正实现应有不变式）、\textbf{差分测试}（自动构造与 PoC 语义相近但不同的输入以检测过拟合）、\textbf{回归检查}（验证合法功能保持）三重机制，系统性抑制过拟合补丁与合法功能回归。
\end{itemize}

\textbf{可行性分析}：（1）直接基于 RRBench：基准、评估框架、五款基线 agent 数据均已就绪，可快速开展对比实验，与课题组前期工作延续性强~\cite{rrbench}；（2）PPT 能力可迁移：研究内容三的"修复意图判定"与本内容的补丁验证需求本质同源，技术路线已形成闭环，风险分散；（3）规约自动提取有先例：ChatAFL 的协议规约提取、Firmalice 的特权模型等已证明 LLM 具备规约理解能力~\cite{chatafl,firmalice}；（4）工程基础成熟：SWE-agent~\cite{sweagent}、OpenHands~\cite{openhands} 等开源框架提供了成熟的修复智能体底座。

\textbf{实验方案}：基准采用 RRBench 全部 115 个案例，后续扩展至 SEC-bench~\cite{secbench}、CVE-Bench~\cite{cvebench} 子集；对比方法包括 SWE-agent~\cite{sweagent}、OpenHands~\cite{openhands}、RepairAgent~\cite{repairagent}、RustAgent、RustForger（即 RRBench 原五款）；评估指标包括 Correct Repair Rate（通过公开+私有验证）、Plausible-but-Private-Rejected Rate、平均迭代轮数、每例成本；消融实验分别验证安全规约引导、PPT 式验证与差分测试的独立贡献。预期 Correct Repair Rate $\geq$ 80\%，私有拒绝率降低 $\geq$ 50\%，在 14 个"无人能修"案例上成功修复 $\geq$ 4 个。

\subsection{基于智能体的漏洞修复验证方法}

\textbf{拟解决的关键问题}：智能体在端到端漏洞修复验证（以补丁存在性测试为核心任务）中的两大瓶颈——\textbf{剥离二进制中的补丁定位}与\textbf{演化补丁识别}。前期实证研究表明，前者占弱模型配置独有失败的 95.2\%，后者是鲁棒性测试的主要失分点~\cite{zhang2026agenticppt}。两者本质上都源于跨抽象层次补丁语义对齐困难、修复意图难以形式化：源码级补丁意图与二进制级指令序列之间存在语义鸿沟，且现有方法过度依赖补丁的形式特征而非修复意图。

\textbf{技术方案}：针对上述问题，本文提出\textbf{语义先验引导的智能体修复验证增强框架}，整体技术路线如图~\ref{fig:verify-route} 所示，包含三个核心模块：

\begin{figure}[htbp]
\centering
\begin{tikzpicture}[node distance=0.45cm]
  \node[module] (m1) {%
    \textbf{模块一：漏洞语义先验提取}（离线，一次/漏洞）\\
    CVE 描述 + 补丁 diff + 源码上下文 $\xrightarrow{\text{智能体推理}}$\\
    漏洞语义五元组 $\langle$触发条件, 危险操作, 干预点, 修复意图, 上下文$\rangle$};
  \node[module, below=of m1] (m2) {%
    \textbf{模块二：语义引导的补丁定位}（在线，核心创新）\\
    粗定位：字符串/常量/导入表启发式 $\rightarrow$ 候选函数集\\
    细定位：五元组约束 + 反汇编切片 $\rightarrow$ Top-K 补丁候选区\\
    置信度排序：基于语义匹配度的候选排序};
  \node[module, below=of m2] (m3) {%
    \textbf{模块三：演化补丁的语义等价判定}（在线，核心创新）\\
    干预点识别：定位补丁实际修改的二进制指令\\
    修复意图比对：判断干预是否实现"修复意图"（而非形式匹配）\\
    不变式检查：验证修复后是否满足语义不变式};
  \draw[arr] (m1) -- (m2);
  \draw[arr] (m2) -- (m3);
\end{tikzpicture}
\caption{基于智能体的漏洞修复验证技术路线}
\label{fig:verify-route}

\begin{itemize}
  \item \textbf{模块一：漏洞语义先验提取}。离线阶段利用智能体从 CVE 描述、补丁 diff 与源码上下文中提取漏洞语义五元组，作为统一语义先验，替代现有方法仅依赖原始补丁 diff 的浅层表示。
  \item \textbf{模块二：语义引导的补丁定位}。在线阶段采用"粗—细"两阶段定位：先用传统启发式（字符串、常量、导入表）快速缩小候选函数集，再将五元组作为约束注入智能体推理，引导其在候选函数中进行语义切片与置信度排序，输出 Top-K 补丁候选区域。
  \item \textbf{模块三：演化补丁的语义等价判定}。针对同一漏洞可能存在多种实现形式的修复（重构、拆分、合并等），不再追求"形式上的补丁匹配"，而是让智能体判断目标二进制中的干预点是否\textbf{实现了与原始补丁相同的修复意图}，并通过语义不变式进行交叉验证。
\end{itemize}

\textbf{可行性分析}：（1）数据基础充分：已构建 561 CVE 高保真基准与 12 组智能体配置的运行日志~\cite{zhang2026pptempirical,zhang2026agenticppt}，包含大量补丁定位与演化补丁的成功/失败案例，可直接用于方法设计与消融验证；（2）技术路线有实证支撑：前期工作已证明"丰富补丁元数据提升 DSR"与"补丁定位是主要瓶颈"两个关键结论，本方案是这两个结论的直接延伸，技术风险低；（3）工具链成熟：智能体框架（Codex / MiniSWEAgent）、二进制分析工具（binutils / Ghidra）与评估基准均已就绪，可快速进入实验迭代。

\textbf{实验方案}：基准沿用前期 561-CVE Source-Built Benchmark + Patch Evolution Set + Ubuntu Packages Set；对比方法包括 Codex 原始配置、Lares~\cite{lares}、PPTSP~\cite{pptsp}、PS\textsuperscript{3}~\cite{ps3}、BinXray~\cite{binxray}；评估指标包括 DSR、Accuracy、补丁定位准确率、每例 token 成本与时延；消融实验分别验证三个模块的独立贡献。预期全配置 DSR $\geq$ 0.98，演化补丁子集 DSR 提升 $\geq$ 15\%，成本增加 $\leq$ 10\%；进一步将验证能力对偶迁移至修复场景，在 RRBench 生成补丁上验证修复正确性判定的有效性。

\subsection{实验方案设计}

\subsubsection{整体评估策略}

三个研究内容的实验遵循统一策略：

\begin{enumerate}
  \item \textbf{基准优先}：每个内容均基于已有或新建的高质量基准，确保可复现与可比较。
  \item \textbf{多维度评估}：从效果（准确率/发现数/修复率）、效率（时间/token 成本）、鲁棒性（跨配置/跨场景）三个维度综合评估。
  \item \textbf{消融驱动}：每个核心模块均设计消融实验，验证其独立贡献。
  \item \textbf{跨内容联动}：设计端到端实验，验证三个内容构成的闭环是否产生协同增益。
\end{enumerate}

\subsubsection{端到端闭环验证实验}

为验证三个研究内容构成的攻防闭环的有效性，设计如下端到端实验：

\begin{enumerate}
  \item \textbf{输入}：一批含已知漏洞的 IoT 固件镜像（部分为真实 CVE，部分为人工植入）。
  \item \textbf{流程}：内容一挖掘未知语义漏洞，产出根因与 PoC；内容二对确认的漏洞进行自动修复，产出候选补丁；内容三对修复后固件进行 PPT 式修复验证，判定补丁是否真正消除漏洞根因；同时内容三对固件中已知 CVE 的修复状态进行补丁存在性核查，覆盖供应链审计场景。
  \item \textbf{评估}：闭环整体准确率、各环节能力复用带来的效率提升、相比独立运行的性能差异。
\end{enumerate}
